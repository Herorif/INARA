# Image atelier and owned local generation

Implemented 14 October 2026. Open **Studio > Image atelier**. The panel offers editable prompts, negative prompts, frame sizes, seed, steps, guidance, preview, PNG/recipe downloads and scoped revision history. It fits the JARVIS workspace on desktop and narrow screens. [Unconfigured desktop](qa/image-unconfigured-desktop.png), [narrow controls](qa/image-mobile-controls.png), [labelled verification preview](qa/image-mobile-preview.png).

**Model configuration remains deferred. No image model was installed, downloaded or run in this milestone.** The normal app disables generation and explains availability until a backend is configured. The UI never substitutes placeholder artwork. QA uses an explicitly labelled checkerboard fixture in a test-only service; production rejects fixture provenance.

## Architecture and organization

`services/creative_jobs.py` now owns the durable request claim, encrypted scope, immutable revisions, bounded artifact reads, timeout/cancellation and Win32 process lifetime previously implemented inside CAD. `creative_transport.py` owns authenticated RPCs and owner-bound approval cancellation. CAD retains its typed recipes, adapter and existing public RPCs. Images supply their own contracts in `images.py`, configuration inspection in `image_config.py`, and RPC adapter in `image_transport.py`. The frontend shares its bounded export/client helpers through `features/creative/client.js`; the previous CAD import remains compatible.

A shared governor lock and active-job registry allow only one CAD/Blender/image job at a time per core. Image generation uses the new `generate_image` permission through the same dispatcher; missing policies require confirmation. Denial, approval ownership/expiry, rechecks and cancellation apply before worker execution. Only authenticated renderer roles can access image RPCs. Last-renderer loss, panel closure, gaming/resident state and core quit stop image work and pending approvals.

Image documents use `image_jobs:<hash(owner + resolved project)>`, separate from CAD. Prompt/settings, job state and artifact metadata are DPAPI protected in the existing database. Completed request IDs return their prior result, conflicting settings reject, and interrupted/uncertain claims never replay automatically. The history cap is 128 claims per owner/project; twelve newest are exposed. Retention/archival remains future work. New revisions use `images/designs/<derived UUID>/` and fresh `images/.work/<UUID>/` staging. Existing files are never overwritten or recursively cleaned. PNG and recipe exports are ordinary project files and include prompt/settings in plaintext; ledger encryption does not encrypt those artifacts.

`image_submit`, `image_list`, `image_cancel`, `image_artifact` and `image_close` are acknowledged RPCs; `image_job` carries scoped progress/results. Binary exports travel through the existing authenticated socket, with no public file server or credential-bearing download URL. PNGs have a 16 MiB ceiling; recipes have a 32 KiB ceiling. The core checks result provenance, expected formats, PNG header/dimensions, recipe consistency, bounded size and SHA-256; downloads/previews recheck size/hash. Browser decode failures are visible. Object URLs are revoked on release, and reconnect retries the preview.

## Local backend contract (setup later)

The first adapter supports local **StableDiffusionPipeline** and **StableDiffusionXLPipeline** Diffusers folders. The operator can later set `INARA_IMAGE_MODEL_DIR` to a previously downloaded compatible model directory and install the optional worker dependencies (PyTorch, Diffusers, Transformers, safetensors and Pillow) in the runtime environment. No dependencies or weights were added to the locked lean core. GPU-specific dependency selection, version locking and real model acceptance are still setup/release work; an incompatible installation fails safely rather than being represented as ready-to-generate proof.

Availability inspection reads at most 16 KiB of model metadata and checks supported pipeline/component declarations plus package presence. It does not import PyTorch, Diffusers or Pillow, load weights, test CUDA or prove model completeness. Custom pipelines/component modules are rejected. Refresh history after setup to update availability. The model directory is operator configuration, never an argument supplied by the model or renderer.

The fixed `workers/image_worker.py` imports `creative/image_backend.py` only after explicit generation. The adapter uses local-only, safetensors loading with Hugging Face/Transformers offline flags and telemetry disabled, CUDA float16 when available or CPU float32 otherwise. It limits Torch CPU threads to two, uses VAE slicing and preserves configured pipeline filtering. Prompt, dimensions, inference steps, guidance and a seeded generator are explicit. The supported dimensions are 512, 768 or 1024 per axis; steps 1-40, guidance 1-15 and seed 0-2147483647. Exactly one image is produced. The implementation follows the documented [local loading controls](https://huggingface.co/docs/diffusers/en/api/pipelines/overview), [text-to-image pipeline](https://huggingface.co/docs/diffusers/api/pipelines/stable_diffusion/text2img) and [step callbacks](https://huggingface.co/docs/diffusers/using-diffusers/callback). Callback phases update the UI; cancellation is enforced by process ownership.

The owned child and descendants receive the existing credential-filtered environment and pipe-only bootstrap. No model-generated code, shell commands, arbitrary worker script, remote service or user-supplied image URL is accepted. The worker re-encodes RGB pixels to PNG without inherited file metadata and records settings, seed, model-folder name, backend and CPU/CUDA device in the recipe. A seed helps repeat a direction; it does not promise identical pixels across changed weights, hardware or library versions. Model weights are not fingerprinted in this first provenance record.

The worker deadline is 180 seconds. Cancellation/timeout closes its atomic Windows Job Object, releasing its process tree. Runtime failures, missing model components, unsupported configurations and memory failures return a sanitized error and preserve previous revisions. This is lifetime management, not an OS security sandbox or automatic VRAM/thermal admission. Large SDXL jobs may exceed the laptop's memory or deadline; actual GPU use, quality and recovery have not been measured. CPU generation may be too slow for this deadline. No cloud image provider, image editing, references, batches, upscaling or model-installation UI is implemented yet.

## Verification and resource evidence

- **144 Python checks and nine frontend checks pass**, plus production build, Ruff and dependency consistency. The existing real Blender check remains skipped because Blender is absent. Image model inference was not run.
- Image checks cover bounds/strict types, missing/invalid setup without tensor imports, custom-component rejection, local-only/safetensors flags and bounded inference settings through mocked SD and SDXL adapters, real owned fixture PNG/recipe exports, encryption, owner/project isolation, hash tampering, duplicate IDs, cancellation, gaming, timeout, shutdown, shared CAD/image admission, permission/duplicate approval handling, SDK schema conversion and final-storage-failure cleanup/no replay.
- `scripts/verify-images.py` runs the actual native host and hidden renderer with fresh profile, projects, settings and protected storage. A test-only service first reports unavailable, then enables a clearly labelled fixture. It verifies disabled generation/no artwork while unconfigured, two real fixture revisions, actual PNG/JSON downloads and dimensions/provenance, panel reopen without regeneration, long-running worker cancellation with earlier revision recovery, no remote assets and widths 1440/768/390. Screenshots were visually inspected. This verifies product plumbing, not image-model quality.
- Three fixture workers start and exit, including the deliberately blocked/cancelled one. Model/worker modules stay out of the resident. After workspace closure, six samples over ten seconds show **65.12-65.18 MB combined working set / 47.51 MB private bytes**, including the venv launcher; before workspace opening, 62.61/46.10 MB. Graceful core stop passes. [Image evidence](qa/image-verification.json). This is short recovery after fixtures, not a diffusion/GPU or real-game benchmark.
- Actual CAD/scene renderer regression also passes after extraction: four geometry workers exit and resident recovery is 65.45-65.46 MB working set / 47.80 MB private bytes. [Regression evidence](qa/image-cad-regression.json). The initial application JS is approximately 242 KB; Image atelier adds a lazy approximately 13 KB JS / 8 KB CSS panel, with shared client helpers separate. Existing Vite/browser-data, large lazy CAD chunk and dependency deprecation warnings remain.

No paid requests, real model inference, Blender, camera, microphone, printer or phone actions ran. Remote CI is configured but unverified. The user deferred the real-game benchmark and provider configuration; WhatsApp replies remain excluded.
