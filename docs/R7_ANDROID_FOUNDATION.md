# R7 Android foundation and secure pairing

Implemented 19 October 2026 within a source/protocol acceptance boundary. The desktop pairing UI and isolated mobile server are verified. Native Android source is present; **APK compilation, Android instrumentation, Keystore execution and Fold8 acceptance are unverified because no configured JDK, Gradle, SDK or ADB is available**. This is not an installable/verified Android release.

## Product behavior

Connections and the command palette now open Android companion, replacing the old phone-control interior in the supported workspace. The responsive JARVIS panel shows listener state, exact address, a two-minute invitation, device-key fingerprint review, paired project/grants and revocation. It polls owner-only pairing state only while open. Invitations leave panel memory on expiry, project changes, disconnect and close; closing cancels unfinished pairing, while an explicitly enabled listener persists until Stop or core shutdown. Invitation secrets are neither broadcast nor stored in renderer localStorage.

The listener is **off at startup**. Enabling it binds a dedicated HTTPS server to one exact RFC1918 IPv4 address or loopback, port 8443 in the UI. Wildcards, public addresses and DNS names are rejected. No discovery, firewall rule, router change or default LAN exposure is introduced. The desktop server remains loopback-only; desktop Socket.IO, settings, tool approvals and user_input are not mounted on the mobile listener.

The app source includes native Compose single/two-pane layouts, a system file picker / paste entry for invitations, connection/approval state, read-only job summaries, bounded image preview and a typed CAD recipe preview. Phone CAD preview is an inspectable recipe/stat representation, not an interactive 3D renderer. Tool-free chat has a separate explicit pairing grant. No phone action/approval, notification or call capability is exposed.

## Identity, scope and transport

A random 256-bit invitation secret has a 120-second in-memory lifetime and is consumed once on a valid claim. Starting another invitation invalidates old unapproved candidates. The owner and resolved project are captured on the desktop; the phone cannot choose an owner or redirect a grant to a new global project. The phone submits a P-256 public key and a possession signature, then waits for the registered unlocked desktop owner to compare its full SHA-256 key fingerprint and approve. Pending/expired/rejected claims have no job/chat/status access. At most eight approved, unexpired devices are allowed. Approved credentials expire after 30 days; revocation tombstones remain durable.

Desktop device records, grants, replay ledgers and TLS key material use existing DPAPI-protected database payloads. A self-signed laptop TLS identity is created only on explicit listener enablement, with an exact-IP SAN, and retained encrypted for reconnect. Temporary key-loading files are password-encrypted PKCS8 with a fresh in-memory password and unlinked after SSL context loading; public certificate files are unlinked too. There is no plaintext private-key fallback. The Android source anchors only the imported laptop certificate in its per-connection trust store and retains hostname validation. Redirects, cleartext, proxy-header trust and browser Origin access are rejected. No public relay or trusted-system-CA-only fallback is supplied.

Every API request signs the UTF-8 bytes `INARA-MOBILE-1`, POST, exact route, device UUID, fresh authentication request UUID, epoch seconds and SHA-256 of the **exact JSON payload string**, separated by newlines. This uses standard TLS and P-256 ECDSA/SHA-256 implementations, not custom encryption. A 30-second clock window and transactional encrypted nonce ledger reject replay across reconnect/process restart. Nonces remain 90 seconds, at most 256 per device; a persisted time high-water check rejects substantial server clock rollback. The isolated API uses a five-second request-body deadline and allows 120 requests/minute globally, eight concurrent connections, at most 64 KiB request bodies, strict extra-field rejection and bounded payloads. Those conservative prototype limits may require tuning after device measurement.

Initial grants are `status:read`, `jobs:read` and optionally `chat:ask`, bound to one device and captured project. Every request checks owner, lock state, device expiry/revocation, key signature, nonce, grant and project containment. Read-only summaries contain twelve recent scoped jobs, not host paths or arbitrary files. Image preview is capped at 2 MiB and validated by the existing contained artifact reader; native decoding also bounds dimensions. Other projects and other devices' conversations reject. Phone history does not migrate desktop legacy transcripts.

Phone chat uses the common ConversationService, encrypted session store and durable request/result ledger, with an **empty dispatcher and tool-free instructions**. Provider-requested tools return unavailable; no approval callback or desktop origin is supplied. Calls, WhatsApp tools, clipboard, files, device control, creative builds and permission mutations cannot run through this channel. Each device permits one in-flight chat; the service permits four globally, with a 30-second provider step and 55-second whole-request deadline. HTTP disconnect, revocation and core closure cancel owned work; authorization is checked again before returning answers.

A stable chat request UUID is separate from each fresh authentication nonce. Retransmitting a completed logical request returns its existing result. An interrupted request stays uncertain; `/receipt` reads it without retrying an AI/tool operation. The app source persists one unfinished item before Send, converts it to uncertain after interruption/process death and requires explicit receipt/discard actions. No automatic outbox send or externally effective action replay exists.

## Android storage and lifecycle source

AndroidKeyStore holds a non-exported P-256 signing key and a separate AES-256-GCM storage key. AES-GCM includes version-specific associated data and fresh IVs; atomic app-private no-backup storage holds link data, bounded cached history/jobs, drafts and the pending item. Missing/corrupt protected state preserves its file and shows explicit recovery instead of overwriting it. Forget is a user-confirmed local erasure, not server revocation. Authorization errors clear cached private views on the next server response; an offline phone cannot be remotely erased by this prototype.

Only INTERNET is declared. There is no microphone/camera permission, notification listener, Telecom/dialer role, foreground service or background worker. Activity stop requests connection/coroutine cancellation and pauses sends. Draft writes debounce, history is bounded by both entries and encoded bytes, response reads are bounded, and cached image decoding checks dimensions. None of these source mechanisms has been executed on Android in this session.

[Android README/build entry](../android/README.md) records the pinned source toolchain, offline-by-default build command, missing build tools and the first-build acceptance work. [Android Keystore guidance](https://developer.android.com/privacy-and-security/keystore), [adaptive layouts](https://developer.android.com/develop/adaptive-apps/guides/support-different-display-sizes) informed the source. Hardware-backed key placement, release signing, dependency verification/locking, APK reproducibility and actual device specifications remain unverified.

## Contracts and acceptance evidence

Six strict owner-renderer socket controls are additive contract-v1 changes. Eight strict HTTPS operations live in an isolated API: claim, finish, status, jobs, preview, chat, history and receipt. The inventory has **69 desktop socket routes, 55 tools (40 model-visible), eight isolated mobile API routes** and the dormant compatibility voice mappings. Mobile models generate TypeScript/schema files; no new model-visible tool was added.

Python fixtures verify single-use/expired pairing, explicit owner approval, role/owner denial, two-device/project isolation, tampering, clock/path/restart replay, grant expiry, revocation/provider cancellation, HTTP disconnect, tool-free idempotent chat, receipts, legacy-history exclusion, preview limits, HTTPS/Origin/body limits and actual loopback TLS with encrypted temporary key loading. Node checks cover explicit listener controls, malformed invitation rejection and closed/disconnected scopes without replay. The shared UTF-8 signature vector is also supplied as a Kotlin JVM test; that test has not been compiled/run.

[Native desktop report](qa/r7-mobile-verification.json) and [UI report](qa/r7-mobile-ui-verification.json) verify the final desktop surface against actual loopback TLS and generated fixture keys. A fixture claims an exported invitation, the UI displays its fingerprint and approves it, signed status/jobs work, nonce reuse and ungranted chat reject, and UI revocation prevents access. The listener is stopped and released before workspace close; core shutdown passes. Screenshots show [desktop fingerprint review](qa/r7-pairing-desktop.png), [390-pixel review](qa/r7-pairing-mobile-width.png) and [tablet-width revocation](qa/r7-revoked-tablet-width.png). No heavy model modules, real phone, provider call, notification access or live call was used. Optional QR encoding (`qrcode==8.2`, [package documentation](https://pypi.org/project/qrcode/8.2/)) is implemented as a lazy adapter but not installed/validated; invitation-file transfer is verified. The native app accepts pasted QR payload JSON; an in-app scanner is not implemented.

773 Python tests and 63 Node checks pass, with one Blender skip. Types, generated-contract drift, Ruff, production web build, source/manifest guards and native loopback TLS/desktop pairing checks pass. The final request-body and embedded-listener refinements also pass the focused 40 Python mobile checks.
